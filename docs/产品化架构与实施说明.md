# 数衡 BankInsight 产品化架构与实施说明

## 已实施范围

当前版本按“保留 NL2SQL 核心、外置产品编排”的方式完成了第一至第五步：

1. 稳定现有 NL2SQL 核心：保留规则优先、LLM 兜底、SQL 安全校验和结果校验；
2. 建立产品契约：新增 `/api/v1` 版本化响应，包含查询编号、字段语义、图表、
   结论、下钻、权限、耗时和告警；
3. 完成 PC/H5 工作台：打通提问、数据、图表、结论和历史；
4. 完成任务4主链：图表推荐、SSE 返回、时间下钻、导出、限时分享和回溯；
5. 完成管理入口：分级权限、敏感数据脱敏、审计事件和管理概览。

原 `/query` 接口保持兼容，现有 NL2SQL 调用方无需立即迁移。

## 模块边界

```text
frontend
  ├─ 智能问数工作台
  ├─ 历史报告
  ├─ 分享报告
  └─ 管理审计

text2sql.api
  ├─ 原兼容接口 /query
  └─ 产品接口 /api/v1

ProductQueryService
  ├─ 权限前置校验
  ├─ Text2SQLService 调用
  ├─ 图表推荐
  ├─ 结构化业务解释
  ├─ 时间下钻
  ├─ 脱敏
  └─ 历史与审计

Text2SQLService
  ├─ 规则/LLM QueryPlan
  ├─ SQL 编译和安全校验
  ├─ 只读执行
  └─ 结果验证与基础答案
```

## 时间下钻口径

当前数据为每日机构指标快照，因此第一版统一采用：

- 年度：每年最后一个有数据日期的值；
- 季度：每季度最后一个有数据日期的值；
- 月度：每月最后一个有数据日期的值；
- 日：原始日值。

接口会返回 `aggregation=period_end`，页面也会明确展示该口径。

当前真实数据粒度只有“日期 + 指标 + 机构”，因此没有伪造
“总行 → 分行 → 支行 → 客户经理”机构下钻。正式接入数据中台后，需要增加：

- `org_level`；
- `parent_org_id`；
- `org_path`；
- 层级有效期；
- 对应层级的指标事实数据。

机构下钻请求应继续由后端根据 QueryPlan 和用户权限生成 SQL，前端不得拼接 SQL。

## 权限模型

第一版提供三个角色：

| 角色 | SQL | 导出 | 分享 | 管理审计 | 敏感指标 |
|---|---:|---:|---:|---:|---|
| viewer | 否 | 否 | 否 | 否 | 具体数值脱敏 |
| analyst | 是 | 是 | 是 | 否 | 按机构授权 |
| admin | 是 | 是 | 是 | 是 | 全量 |

演示环境通过请求头传递身份。正式部署时必须由银行统一身份认证适配器注入，
不能信任浏览器自行提供的角色和机构范围。

对于限定机构范围的用户，当前安全策略要求问题中明确指定机构；全省查询或
未指定机构的查询会被拒绝，避免先执行后过滤造成越权读取。

## 历史、导出和分享

- 查询历史、QueryPlan、SQL、结果、图表和结论保存在产品数据库；
- Excel/CSV 由后端生成，并记录导出审计；
- 分享令牌仅保存哈希，默认 24 小时有效，最长 168 小时；
- 分享访问会按当前访问者权限重新校验和脱敏；
- 当前 SQLite 用于比赛和单机演示，正式环境需替换为目标国产数据库；
- 正式环境还应增加分享撤销页面、对象存储、水印和导出异步任务。

## 业务解释边界

当前解释仅基于已验证的查询结果和已有规则，区分：

- 数据事实；
- 对标或趋势判断；
- 需要额外证据的业务归因。

趋势和变化类问题会明确提示：业务原因需要营销活动、产品、渠道或客户明细
进一步验证。系统不会仅凭一个增长率断言“由年末揽储导致”。

后续接入营销中台、风控中台和业务事件知识库后，可将证据来源、事件编号和
归因置信度补入 `insight` 契约。

## 国产化与中台对接预留

当前生产化改造应继续保持以下可替换边界：

- 身份适配器：银行统一身份、机构和角色；
- 数据执行器：DuckDB → 数据中台或目标国产数据库；
- 持久化仓储：SQLite → 目标国产数据库；
- 模型适配器：OpenAI 兼容接口 → 银行私有模型网关；
- 文件存储：本地内存响应 → 银行对象存储或文件平台；
- API 网关：认证、国密、签名、限流和链路追踪。

确定联合银行实际 CPU、操作系统、数据库、中间件、国密和离线要求后，再进行
兼容性验证。容器化本身不等同于国产化认证。
